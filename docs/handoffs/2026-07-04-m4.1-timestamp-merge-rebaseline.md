# 2026-07-04 M4.1 Timestamp-Merge Re-baseline

## Reason

M3/M4/M5 now use `timestamp_merge` as the canonical value-change regime. This
matches the buds-lab implementation pattern of shifting timestamps by a timed
delta and merging back on timestamp keys. The older `row_offset` and
`row_offset_meter_aware` regimes remain available for historical ablation and
M5 regime-ladder interpretation.

## Changed

+ `src/lead/features.py` defaulted `add_value_change_features(...)` to
  `value_change_regime="timestamp_merge"` without changing the underlying
  row-offset or timestamp-merge logic.
+ M3 runners now pass `value_change_regime="timestamp_merge"` explicitly and
  write provenance for the canonical regime.
+ Added `scripts/run_m3_2_baseline.py`, which reuses
  `scripts/run_m4_3_timestamp_value_change.py::fit_m3_2_regime` and gates
  M3.2 against the timestamp-merge reference AUC.
+ INV-4 through INV-8 default to `timestamp_merge`; INV-1 and M4.3 remain
  explicit multi-regime studies.
+ M5/M6 comparison defaults remain `timestamp_merge`; legacy row-offset JSON
  stays under `data/processed/legacy/`.
+ `tests/golden_metrics.json`, `docs/metrics/m3-50-50-ensemble.json`, and
  `docs/reports/m3-report.md` were re-baselined to timestamp-merge outputs.
